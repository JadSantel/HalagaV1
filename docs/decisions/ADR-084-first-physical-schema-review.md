# ADR-084: Set First Physical Schema Review Choices

- Status: Accepted
- Date: 2026-10-12
- Supplements: ADR-069, ADR-072, ADR-083

## Context

The first Prisma domain schema is a candidate for the laptop reference path. Its review draft left money precision, diagnostic answer shape, identifier generation, revision boundaries, and migration scope open. The first migration must preserve the product's exact PHP amounts and accepted laptop diagnostic history without settling deferred category or publication policy.

## Decision

- Store monetary amounts as exact PHP values with two decimal places (`Decimal(12,2)` for the current seller price expectation). Centavos are supported. This is a precision choice, not a product maximum; do not impose a business maximum without a separate decision.
- Store diagnostics as one JSON answer value per question, keyed by item group, schema version, and question key. Preserve the accepted laptop diagnostic version and submitted answers with the listing revision. Do not define diagnostic schemas for other categories here.
- Keep UUIDs generated by Prisma's application client, as represented by the candidate schema.
- Keep listing content revision-scoped: item groups, diagnostic answers, ownership declarations, and media references attach to a listing revision. Listing identity and lifecycle, cycle history, and public-availability intervals remain separate records. Revision immutability remains a guarded write-path requirement.
- Scope the first domain migration to the account/listing foundation represented by the candidate, not negotiations and reservations. Add and review the single-active-reservation database invariant before implementing or migrating negotiation/reservation flows.
- Do not create or apply a migration until the Better Auth adapter-generated schema is aligned with the separate `user_account` mapping and the migration SQL includes the required reviewed constraints. Consequential publication commands also require audit/outbox support before implementation.

## Consequences

- PostgreSQL `numeric(12,2)` bounds storage capacity but does not establish a product-level maximum. Server validation must use exact decimal values and enforce the applicable amount rules.
- `diagnostic_answer.answer` remains flexible JSON. Server validation against the versioned laptop question definition is required; JSON storage does not validate answer semantics.
- `docs/architecture/PHYSICAL_SCHEMA_CONSTRAINTS.sql` records SQL-only checks that Prisma schema syntax does not express in this candidate. Keep it aligned with checked-in migrations when those are created.
- This decision does not settle renewal limits, renewal grace periods, newest-sort behavior, or non-laptop diagnostic readiness.

## Implementation record

The first foundation migration now includes the Better Auth CLI-generated core tables, an explicit restrictive identity-to-domain FK, and the reviewed SQL checks with corrected Prisma column names. Publication availability uses a composite cycle/listing FK plus the native PostgreSQL `btree_gist` extension and a GiST exclusion constraint to prevent overlaps across cycles. Verify extension support when selecting hosting. History updates are rejected by triggers; authorized retention deletion remains separate and must not be blocked indefinitely.

These mechanisms implement existing history, integrity, and exposure rules. They do not implement marketplace authorization, publish/renew commands, matching completion, retention execution, or audit/outbox services. The prerequisites for creating the first migration are satisfied; consequential commands still require their documented gates.

## Local synthetic draft implementation record (2026-10-19 PHT)

The owner's bounded Slice 3 request authorizes authenticated owner-private,
potentially incomplete single-item laptop drafts. The additive
`20261019090000_incomplete_laptop_drafts` migration makes revision barangay and
item-group condition nullable. This represents unselected geography and answers
that cannot yet support a validated condition, without inventing geographic data
or treating invalid/incomplete data as `Untested/unknown`. Publication requirements
are unchanged and no publication command is implemented.

POST and owner-only GET/PUT draft routes recheck the undeleted mapping and exact
stored session under identity/domain/session locks. Clients supply a request UUID,
not seller/author identity. The UUID becomes the immutable revision ID for retry
deduplication; saves require the expected current version. All writes append
revision/group/answer history and advance the pointer atomically while staying
`DRAFT`. Versioned question rows also preserve the accepted behavior and included
items multi-select arrays and their details. Existing whole-draft/per-answer server
validation gates derived-condition persistence; incomplete or invalid disclosures
and safety-stop answers remain private with null conditions.

Reads select an explicit owner-private detail; there is no public reader, staff
grant or marketplace grant. Unverified authenticated users may work on these
synthetic drafts, following the owner's request; this does not change publication
eligibility. Drafts generate no asynchronous work or notifications. Immutable
revision ID/author/target/version/time record the private save history with a fixed
draft state; this does not implement or waive consequential publication audit/outbox
requirements. Controlled CDO geography, media, declaration/fulfillment submission,
safety/risk/restriction checks, audit/outbox and launch gates remain unresolved or
unimplemented as applicable. Retention/deletion remains separately gated; history
is not authorized for indefinite retention. See
[LAPTOP_DRAFT_LOCAL_TESTING.md](../LAPTOP_DRAFT_LOCAL_TESTING.md).
